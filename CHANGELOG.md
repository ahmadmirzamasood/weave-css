## 0.1.0-rc.2

Release candidate for 0.1.0 (not yet published). Supersedes 0.1.0-rc.1, which was prepared but never published or tagged.

- The command is now `weavec` (was `weave`), because the name `weave` is used by other command-line tools (the `weave-cli` crate, a Homebrew formula). The language, the `.weave` extension, the packages `weave-css` and `weave-compiler` and all flags and output are unchanged. `watch` status lines now start with `[weavec]`; release archives are named `weavec-<version>-<target>`. Update scripts and editor task matchers that run `weave` or match `[weave]`.

## 0.1.0-rc.1

Prepared, never published. Its entries are kept because they describe the work leading to rc.2.

Release candidate for 0.1.0 (not yet published to any registry or as a GitHub release). The v0.1 language is implemented except the `color` built-ins (error E5001). Bullets below record the work from the first specification to this candidate, in phase order, newest first.

- Phase 11: release preparation. Version `0.1.0-rc.1` for every package; the CLI package is renamed from `weave-cli` to `weave-css` (the name `weave-cli` is taken on crates.io and `weave` too; the installed binary is still `weave`; the library stays `weave-compiler`). Both published packages carry registry metadata, a README and a LICENSE copy, and ship only `src/`, the README, the license and the manifest. `weave-bench` and the new `weave-docs` test harness are never published.
- Documentation: new README, installation guide, tutorial, library API guide, compatibility policy, benchmarks page, release procedure and release notes (docs/); `THIRD-PARTY-NOTICES.md`. The tutorial and README examples are compiled by `crates/weave-compiler/tests/docs.rs`, the library guide's Rust examples by the `weave-docs` crate's doctests, and the compiler crate's README as its doctest.
- Release machinery: `.github/workflows/release.yml` (pinned actions; tests, packaging dry run, native builds for Linux x86_64, macOS arm64 and Windows x86_64, version and example smoke tests of the built binaries, Linux reproducibility check, deterministic archives, `SHA256SUMS`, and only on explicit request build-provenance attestation and a draft GitHub release); `scripts/package_release.py`; `scripts/check_release.py`, which CI also runs.
- `weave --version` and `--help` no longer say "pre-alpha" or name a phase.
- Decision recorded for the evaluation-step default (security review F-08): the default of 1,000,000 steps is unchanged; plain CSS with more than about 333,000 simple rules needs `--limit evaluation-steps=…`, now documented in docs/CLI.md.
- The wall-clock budget of the test `functions::comparison_bombs_are_bounded` is 120 s instead of 20 s: it detects a hang, and 20 s was flaky on a loaded machine.

- Phase 10: hardening. New `fuzz/` crate (separate workspace, nightly + cargo-fuzz 0.13.2, libFuzzer) with `lex`, `parse` and `compile` targets, a seed-corpus builder from the repository's fixtures and examples, a Weave/CSS dictionary, a Docker environment and a non-required 60-second "Fuzz smoke (nightly)" CI job. The compiler's new `fuzzing` cargo feature exposes the tokenizer and parser invariant checks (`weave_compiler::fuzzing`, not a stable API, no dependencies); `tests/fuzz_replay.rs` replays them on every fixture, example and stored regression on stable.
- Fixed superlinear compile time on untrusted input: duplicate-key detection in map literals, duplicate parameter names, duplicate or misplaced named arguments, and named-argument binding were quadratic (a 1 MiB input could take minutes). Dependency-graph post-processing and watch invalidation are now linear too. Output and diagnostics are unchanged.
- The filesystem resolver reads only regular files: a FIFO, directory or device named like a module is E7001 instead of blocking the build. docs/CLI.md documents root confinement and its limits against concurrent writers.
- Diagnostics also escape U+2028 and U+2029; `weave watch` status lines escape the output path.
- New tests: `tests/security.rs` (every resource limit's diagnostic, linear-time regressions, malformed encodings, every byte prefix of a Unicode source, forged diagnostic lines), a Windows directory-junction escape test that runs without privileges, and a Unix special-file test.

- Phase 09: performance. New `weave-bench` workspace crate (unpublished) with seven deterministic benchmark workloads and in-process warm, cached and incremental scenarios that check every build's output; `scripts/bench.py` measures cold processes, peak memory and environment, and compares a baseline checkout in interleaved rounds. New library API `compile_observed` and `Phase` report build phases to a caller-supplied observer (the compiler still reads no clock).
- Faster builds with byte-identical output: fewer allocations while parsing templates, small-list scopes and lazily formatted diagnostics labels in the evaluator, and one canonicalization per path per build in the CLI resolver (also reused by the output collision check). On the reference machine cold builds are 12–48 % faster on the large, module-graph and function-heavy workloads; small files are unchanged within noise.
- The module cache key now explicitly includes the compiler version; trees are not cached from parses that started or ended with a full diagnostic list; entries for modules the latest build no longer reaches (renamed, deleted, unloaded) are dropped. New incremental tests compare every cached build with an uncached one across edits, deletions, renames, missing-file recovery, relocation, limit changes and source maps.

- Publish the repository with license, security policy and contribution guide.
- Add the Weave v0.1 language specification: docs/LANGUAGE.md, docs/grammar.ebnf, docs/TYPES.md, docs/CSS-COMPATIBILITY.md; 35 specification fixtures in tests/fixtures/spec (pending a compiler runner).
- Notable v0.1 choices: `rule` takes a raw CSS selector prelude; statement keywords always start statements; `load` must precede other statements; CSS fragment literal `` `…` ``; `\#{` literal marker; parent lists with more than one selector lower to `:is()`.
- Add CI: specification consistency checks (`scripts/check_spec.py`) and Rust format/clippy/test jobs on Linux, macOS and Windows that activate once a Cargo workspace exists.
- Add the Rust workspace (phase 02): `weave-compiler` library and `weave-cli` with a `weave` binary. Development toolchain Rust 1.99.1 (rust-toolchain.toml), MSRV 1.85, edition 2024, no third-party dependencies, unsafe code forbidden.
- Compiler foundation: source manager with byte spans, line/column (scalar values) and UTF-16 columns; E0001 invalid UTF-8 and E0006 U+0000 detection; diagnostics with stable codes, labels, notes and terminal-safe rendering; validated resource limits with the LANGUAGE.md §17 defaults; module resolver trait with load-path validation, an in-memory resolver and a root-confined filesystem resolver in the CLI.
- New diagnostic E5001 (feature not implemented by this build), LANGUAGE.md §16. `weave build`/`weave check` validate the input and then fail with E5001; no CSS is produced yet.
- CI: pinned toolchain from rust-toolchain.toml, MSRV 1.85 test job and dependency policy check (`scripts/check_deps.py`).
- Phase 03: compile the plain-CSS subset. A CSS Syntax Level 3 tokenizer with byte spans and the Weave `#{…}`/`\#{` extensions; a parser implementing item classification, declarations, `rule` at stylesheet level, the at-rule and context matrices, `opaque` blocks, unknown at-rules and `/*!` comments; an emitter for the v0.1 output format. Unsupported Weave constructs (bindings, control flow, functions, recipes, modules, exports, `fail`/`warn`, interpolation, nested rules and nested group at-rules) are reported as E5001.
- New diagnostics in use: E0002–E0005, E0101–E0104, E0110, E0111, E4012, E4013, E6001–E6003, E6005, E6006, E6008, E7010, E8002, E8006. Recovery is bounded; block parsing, selector normalization and emission use explicit stacks, so the largest nesting limit (4096) runs on a 2 MiB stack.
- `weave build` writes CSS to stdout and `weave check` validates without output (exit 0 on success, 1 on errors).
- Executable fixture runner (`crates/weave-compiler/tests/fixtures.rs`): 30 new fixtures in `tests/fixtures/css` must pass; the 35 specification fixtures are classified pass/pending/fail (4 pass, 31 pending on E5001, none fail). Specification fixture status is now `specification`; `scripts/check_spec.py` also checks the new fixture set.
- Test-only dependency `cssparser` 0.38.0 (MPL-2.0, default features off; with `dtoa-short` 0.3.5 MPL-2.0, `dtoa`, `itoa`, `smallvec`) as an independent CSS parser for validating emitted CSS. `scripts/check_deps.py` allows MPL-2.0 only for reviewed dev-only packages and fails if one becomes a normal or build dependency.
- Specification clarifications (LANGUAGE.md §3.2, §12, §13; CSS-COMPATIBILITY.md §3): the `{` of `\#{` balances like any `{` (E0111 outside custom properties); unmatched or unclosed brackets are E0005 and line breaks in strings E0002; comments in selectors and preludes act as whitespace; unknown at-rule extent and balanced scanning follow CSS Syntax; `@import`/`@namespace` only at module top level; `@charset` exactly `"UTF-8"`.
- Phase 04: values, scopes and interpolation. Immutable `bind` with block scopes (use before `bind` in the same block is E1003; duplicates E1001); numbers with units (binary64, six-decimal quantization, magnitude ≤ 1e12, exact unit conversions), strings, 8-bit hex colors, booleans, lists and insertion-ordered maps; operator precedence, non-associative comparisons and short-circuit `&&`/`||`; member and index access; `#{…}` interpolation in values, CSS strings, URLs, selectors, property names, known preludes and keyframe selectors with context-specific escaping; the `css.space`, `css.comma`, `css.slash`, `css.ident` and `css.fragment` constructors. Bare identifiers, `var()`, `calc()`, `env()` and unknown functions stay CSS.
- Interpolation can never change CSS structure: values are quoted or escaped per context, fragments are validated (including a new rule against lone `\`), comment openers formed across an interpolation boundary are rejected (E2003), and every interpolated region is re-checked (E2003, E6007, E6003).
- New diagnostics in use: E0007, E0112, E0113, E1001–E1004, E2001, E2003–E2009, E2011, E3001–E3004, E4001–E4005, E6007, E7003, E8004, E8007. Other specified built-ins and `range` are E5001.
- Expressions compile to postfix ops evaluated on a value stack, so expression nesting up to the 4096 limit runs on a 2 MiB stack; interpolation nested inside strings and fragments is limited to 64 levels (LANGUAGE.md §17).
- Fixtures: new `tests/fixtures/values` set (14 cases, all must pass); 17 of the 35 specification fixtures now pass (18 pending, 0 fail); css fixture 024 now lists only constructs that remain unimplemented. Specification clarifications in LANGUAGE.md §4.2, §5.3, §7.1, §7.3, §17 and TYPES.md §7.
- Not implemented yet: control flow, functions, recipes and the other built-ins (phase 05), nesting (phase 06), modules (phase 07), source maps and output files (phase 08).
- Phase 05: functions, control flow and recipes. Typed `fn` definitions with defaults, named arguments, `yield`, recursion and hoisting; `when`/`otherwise when`/`otherwise`; `each` over lists (with index) and maps (insertion order); recipes with parameters, `apply`, content blocks evaluated in the caller's scope and `slot`; `fail` (E9001) and `warn` (W9001). Functions see only their module and cannot emit CSS (E4014).
- New built-in reference docs/BUILTINS.md: `range` and the `math`, `list`, `map`, `string` and `meta` namespaces are implemented; `color` remains E5001.
- Evaluation no longer recurses per call: expressions, templates, argument binding and function bodies run as tasks on an explicit stack, so the largest call depth (4096) runs on a 512 KiB thread. The call-depth limit (E8003), evaluation steps (now also statements, iterations, emitted items and produced text/collection sizes, with a budget for value comparisons) and the output limit are enforced during expansion; recursion, expansion, collection, string and comparison bombs fail with a diagnostic.
- Recipe output is checked where it is expanded (E6001, E6002, E6003, E6005). Errors inside calls carry labels pointing at the call sites and parameter declarations.
- New diagnostics in use: E2002, E2010, E3005, E4006, E4007, E4010, E4011, E4014, E8003, E9001, W9001.
- Fixtures: new `tests/fixtures/functions` set (12 cases, all must pass) and `crates/weave-compiler/tests/functions.rs`; 25 of the 35 specification fixtures now pass (10 pending on nesting and modules, 0 fail). Specification clarifications in LANGUAGE.md §4.3, §8, §9, §10, §17, §18 and TYPES.md §9.
- Not implemented yet: nesting, including nested rules and at-rules produced by recipes (phase 06); modules (phase 07); `color` built-ins.
- Phase 06: nesting and full CSS rule contexts. Nested `rule`s are parsed structurally (a new selector module) and lowered with CSS Nesting semantics: `&` is substituted directly only where provably equivalent, otherwise replaced by `:is(<parent list>)`; never Cartesian expansion. Parent references in every position (leading, after other compounds, inside `:not()`/`:is()`/`:where()`/`:has()`/`:nth-child(… of …)`), implicit descendant and leading-combinator relative selectors, selector lists at every level.
- Declarations before, between and after nested rules become rule segments in source order; `opaque` blocks, unknown at-rules and `/*!` comments stay in their segment. `@media`, `@supports`, `@container`, `@layer` and `@starting-style` nested in rules are lowered by wrapping; nested `@media` is never merged; empty nested group rules are omitted, empty `@layer` blocks kept.
- Recipe bodies and content blocks may now contain nested rules and known at-rules; their placement is checked where they are expanded (E6001, E6002, E6004–E6007). `@font-face`, `@keyframes`, `@property`, `@page`, `@scope`, `@layer` statements and `@font-feature-values` from a recipe applied at stylesheet level are emitted.
- New diagnostics in use: E6004 (nested rule under a pseudo-element), E8005 (selector expansion: the summed weight of lowered nested selectors, counting copies of parent lists inside `:is()`); E6007 now also covers invalid nested selectors (empty list items, dangling or doubled combinators, type selectors after `&`, including `&-suffix`). Lowered selector text is bounded by the output limit before it is built.
- Evidence: `crates/weave-compiler/tests/nesting.rs` compares the specificity of every lowered selector with the native definition for 12 parent lists × 18 nested selectors (and × 5 middle levels), using an independent calculator; `scripts/browser_check.py` compares computed styles of lowered CSS with native CSS Nesting in headless Chrome (8 cases, each also detecting a naive lowering), also run in CI as "Browser computed styles". New `tests/fixtures/nesting` set (9 cases); 31 of the 35 specification fixtures pass (4 pending on modules, 0 fail).
- Specification clarifications in LANGUAGE.md §11, §17 and CSS-COMPATIBILITY.md §2, §4.1, §4.3, §4.4, §8: a nested selector starting with a combinator is relative even when it contains `&`; no suffix concatenation; the E8005 measure; segments match per selector like nested declarations rules.
- Phase 07: modules. `load "./path.weave" as name;` with explicit relative paths resolved from the importing file, canonical module identity, `export` for top-level `bind`, `fn` and `recipe`, and namespaces with read-only access to exported members (`ns.value`, `ns.fn(…)`, `apply ns.recipe`). Private and missing members are E7003; functions and recipes always run in their defining module; loaded modules cannot see their importer.
- Loading is a depth-first traversal on an explicit stack: each module is read, parsed and evaluated once per build (diamonds and repeated loads included), and CSS is emitted dependencies first, at first encounter, entry last. Cycles are E7002 at the closing `load`, with the full chain; `load` after other statements is E7005; resolver failures and module/input limits are reported at the importing `load`.
- Native `@import`/`@namespace` order is checked across modules after concatenation (E7010, with a label at the earlier CSS and its module); CSS is never reordered except that the entry module's leading `@charset` is emitted first. `@charset` in a loaded module is E6008.
- Library API: `compile_with_cache` and `ModuleCache` (parsed modules reused only for byte-identical source, same role, nesting limit and file position; `invalidate`/`clear` hooks; hit/miss statistics), `DependencyGraph` on every `Compilation` (dependencies, dependents, `affected_by`, emission order; partial on failure). Persistent incremental correctness is not claimed.
- CLI: the filesystem resolver is tested for canonical identity, `..` confinement and symbolic links inside and escaping the root (file and directory links on Unix; on Windows the link test runs only where links can be created).
- New diagnostics in use: E7001, E7002, E7004, E7005, E7006, E8008. Tests: new `crates/weave-compiler/tests/modules.rs` (34 tests, all through the in-memory resolver); all 35 specification fixtures pass. css fixture 024 now covers only the `color` built-ins.
- Phase 08: developer tools. `weave build`, `check` and `watch` with stdin input (`-`), `--output <file|->` (outputs replaced atomically through a temporary sibling file, only after a successful build), `--root <dir>` for module confinement, `--diagnostics human|json` (one JSON object per build), `--deps <file|->` dependency lists, repeatable `--limit <name>=<n>` overrides and `--poll-interval`. Exit status 0/1/2. Commands run on a 64 MiB thread, so the largest nesting limit works from the CLI. Reference in docs/CLI.md.
- Output safety: `.weave` output paths are refused; outputs are compared with every module of the build and with each other after resolving symbolic links (case-insensitively on Windows and macOS), and a collision writes nothing.
- `weave watch` polls file metadata with the standard library (same behaviour on Linux, macOS and Windows), watches every loaded module and every tried `load` path, so it follows module creation, deletion, renaming and graph changes, never watches its own outputs, and keeps the last successful output when a build fails. Parsed modules whose text is unchanged are reused from the module cache.
- Source maps (ECMA-426): `--source-map[=file|inline]` and `--source-map-content`. One mapping per emitted item, pointing at its definition location (inside recipe bodies, content blocks and loaded modules; lowered nested rules at their `rule`); UTF-16 columns in CSS and sources; paths relative to the CSS file; no embedded source text unless requested. Library API: `CompileOptions::source_map`, `SourceMap` (with the `apply` chain of every mapping), `JsonOptions`. `CompileOutput::source_map` is now `Option<SourceMap>`.
- Editor support in editors/: a TextMate grammar and VS Code language configuration for local installation (not published, not a language server), configuration examples, and `scripts/check_editor.py` (run in CI).
- Examples in examples/ (the LANGUAGE.md §20 example, a modular design system, nesting), each built and compared by the CLI tests.
